# Product Analytics & Data Reliability Workbench

**Version:** v0.22  
**Stack:** Python · DuckDB · SQL · Pandas · NumPy · SciPy · Statsmodels · Pytest · GitHub Actions

A reproducible analytics workbench for a synthetic portfolio of subscription products. The project is designed around a practical question:

> When a product KPI moves, can the team trust the number, explain the movement, and make a defensible decision?

The repository combines data-pipeline reliability, metric contracts, forecasting gates, experimentation, and risk-aware experiment design in one auditable workflow.

## What the project demonstrates

| Capability | Example evidence |
|---|---|
| Pipeline correctness | Controlled faults create **9.2–12.2% raw revenue overstatement** before validation/reconciliation. |
| Metric semantics | The same synthetic funnel gives **18.0%** conversion from first-open and **56.6%** conditional conversion from trial-start; both are correct under different contracts. |
| Forecast governance | In the reference run, **3 DAU forecasts pass** the planning gate while **6 revenue/subscription forecasts are withheld**. |
| Safe recovery | An idempotent backfill changes the corrected KPI on the first run and produces **£0.00 second-run delta**. |
| Experiment design | A planning candidate shifts a risky price test from 50/50 to **20/80**, reducing higher-price exposure from **350 to 219 users (37.4%)** for comparable planned information, at the cost of more total traffic and a longer readout. |

All numbers above are generated by the synthetic/reference workflow or planning stress tests. They are **not production-company results**.

## Core design

### 1. Bronze → Silver → Gold

- **Bronze** preserves generated raw events, including controlled faults.
- **Silver** normalises types, removes invalid duplicates, applies identity/timestamp checks, and records validation outcomes.
- **Gold** calculates daily product metrics from certified Silver rows only.

The goal is not to hide bad data. The goal is to keep bad-data evidence observable while preventing it from silently entering certified metrics.

### 2. Metric contracts

Metric names are not treated as definitions. Each metric has an explicit numerator, denominator, unit, grain, and version.

For example, the project distinguishes:

```text
paid_conversion_from_first_open
paid_conversion_from_trial_start
```

This avoids presenting two valid but semantically different conversion rates as if they were contradictory.

### 3. Forecast gate

Forecasts are evaluated with rolling-origin backtests. A model can be statistically valid to fit but still be **withheld from planning** if its holdout error or stability requirement is not met.

This separation is deliberate:

```text
model runs successfully != forecast approved for a business decision
```

### 4. Experiment guardrails

Pricing experiments separate the commercial estimand from a customer-safety guardrail. Revenue upside is not allowed to mathematically compensate for a harmful paid-conversion state.

### 5. Risk-aware randomisation

The experiment-design module treats treatment allocation as a decision variable. It searches candidate allocations only after checking separate constraints for:

- commercial tail risk;
- expected risky-treatment exposure;
- portfolio concentration;
- readout horizon.

Among feasible candidates, the default policy is lexicographic: minimise risky-treatment exposure first, then prefer faster readout. There is no opaque weighted score.

The current reference planning candidate is **20% higher-price / 80% control**. It is a design to validate, not a production recommendation: arm-specific variance and realised traffic must be re-estimated before use.

## Quick start

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python scripts/run_workbench.py --output-dir build/reference
pytest -q
```

Or:

```bash
make reference
make test
```

## Reproducibility

The reference workflow uses fixed seeds and writes machine-readable outputs under `results/` / the chosen build directory. Tests cover:

- deterministic generation;
- duplicate and revenue-fault detection;
- metric-denominator semantics;
- idempotent replay/backfill behaviour;
- forecast approval logic;
- experiment guardrails;
- risk-aware allocation constraints.

GitHub Actions installs the full dependency set and runs the test suite on every push and pull request.

## Scope and limitations

This repository uses **synthetic product data** so that faults, causal assignment, and planning scenarios are known and reproducible. The purpose is to demonstrate analytical and engineering reasoning, not to claim external business impact.

Risk budgets and cross-product stress parameters are explicit planning inputs rather than universal thresholds. Any real deployment would require re-estimating traffic, arm-specific variance, outcome maturity, and operational guardrails from the target product system.
