# Results and interpretation

This repository contains two deliberately separate evidence classes. All underlying data are synthetic.

## A. Current v0.23 reproducible evidence

Run:

```bash
python scripts/run_workbench.py --output-dir build/reference
python scripts/validate_build.py build/reference
```

The current workflow regenerates:

- raw Bronze events with controlled faults;
- certified Silver events;
- row-level rejected events with `reject_reason`;
- Gold daily metrics;
- product-level revenue reconciliation;
- nine forecast evaluations (three products × three metrics);
- machine-readable event and metric contracts;
- quality counts and a SHA-256 manifest.

The validator checks semantic invariants rather than hard-coding a desired business result. In particular, it requires complete row accounting, non-empty reject reasons, all configured products in revenue reconciliation, the expected forecast set and matching artifact hashes.

### Data reliability interpretation

Controlled duplicate purchase faults are intentionally visible in Bronze revenue. Certification removes the duplicate rows from Silver/Gold while retaining the rejected records. Revenue reconciliation therefore answers both questions:

1. how much did the raw metric move because of invalid data? and
2. which concrete rows explain the difference?

### Metric semantics

Two conversion contracts intentionally answer different questions:

- paid users / first-open users;
- paid users / trial-start users.

The difference is semantic rather than contradictory. The generated metric registry stores numerator, denominator, grain, unit and version.

### Forecast governance

DAU, revenue and paid-subscription baselines are evaluated per product. A forecast can execute successfully yet still be withheld from planning if its holdout evidence fails the declared gate.

## B. Preserved planning snapshots

The files under `results/` retain selected numerical snapshots from the broader pre-v0.23 decision-design study. These include the previously reported conversion percentages, forecast counts and the risk-aware 20/80 price-test planning example.

They remain useful as methodological examples, but the compact public v0.23 package does **not** claim that every historical number is regenerated by the current reference script.

In particular, the 20/80 allocation snapshot came from a larger Monte Carlo portfolio-risk study. The current package retains the allocation mathematics and risk-budget objects, but not the entire historical simulation engine.

For that snapshot, the earlier planning comparison was:

| Design | Total users | Higher-price users | Approx. readout |
|---|---:|---:|---:|
| 50/50 | 700 | 350 | 184 d |
| 20/80 candidate | 1,094 | 219 | 270 d |

This is a **planning snapshot, not a production recommendation**. The original analysis also showed sensitivity to arm-specific variance, which must be measured before adopting an unequal allocation.
